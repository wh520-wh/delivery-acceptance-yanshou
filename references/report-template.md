# 验收报告模板

> 落盘到 `<计划文件同目录>/<计划名>-acceptance-report.md`。用产品语言 + 证据，少用内部术语。

```markdown
# <计划名> 验收报告

> 验收对象：<计划文件路径>
> 验收方式：计划对照 + 源码审查 + 真实测试运行 + 边界探针

## 一、计划完成度：XX%（Task 1-N 状态）

| Task | 内容 | 提交 | 结论 | 证据 |
|------|------|------|------|------|
| 1 | ... | <hash> | ✅完成 | ... |
| ... |

评审硬伤对账（A1-AN）：逐条 ✅/❌ + 证据。
Self-Review 声明的"本期不做"：是否与实现一致。

## 二、代码质量：良好（X/5）

优点：...（分层、命名一致、误报防护、注释 why）
扣分项：...（近似值精度、不对称校验等）

每维度 1-5 分表 + 总体评级 + Top 3 改进建议。

## 三、Bug 审计：X 个确认 bug，Y 个疑似

（先说明跑了哪些测试拿基线 + 写了哪些探针）

| 编号 | 严重度 | 位置 | 描述 | 影响 | 状态 |
|------|--------|------|------|------|------|
| B1 | 低 | file:line | ... | ... | 已验证复现 / 疑似 |

每个 bug 附探针输出片段作为证据。区分确认 vs 疑似。

## 四、执行者水平评价

3-5 段，从计划执行力、TDD 纪律、诚实守规、代码品味、提升空间五方面。
给一个总评（资深/合格/需提升）。

## 五、改进点清单（按 P1/P2/P3）

| # | 优先级 | 问题 | 已验证 | 详见 polish 计划 Fix |
|---|--------|------|--------|---------------------|
| 1 | P1 | ... | ✅ | Fix 1 |
| ... |

## 六、最终审查（修复后）

- 逐 Fix 独立验证：每个 Fix 探针结果（应/实测）
- 全量回归：X/X 全绿
- 依赖方向核查：无循环依赖
- 子代理诚实披露核查：...

## 七、可合并判定

✅ 可合并 / ⚠️ 修复后可合并 / ❌ 不可合并
理由：...
```

## 评分约定

- 计划完成度：百分比（已落地 Task / 总 Task；可选门按计划豁免条款判断，不简单判"未完成"）。
- 代码质量：良好/优秀/合格/不合格 + 五维 1-5 分。
- Bug：数量 + 严重度分布，区分确认 vs 疑似。
- 执行者水平：资深/合格/需提升 + 具体维度。
- 可合并判定：三维度 + 复审综合，给明确 ✅/⚠️/❌。
