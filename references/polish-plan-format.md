# TDD polish 计划格式

> 落盘到 `<计划文件同目录>/<计划名>-polish.md`。复用 superpowers/writing-plans 的 plan 风格。每个改进点一个 Fix，严格 TDD。

## 文件头

```markdown
# <计划名> 收尾改进计划

> 目标：修复验收中确认的 N 个点（X 个 P1、Y 个 P2、Z 个 P3），全部 TDD，不破坏既有测试。
> 执行方式：superpowers TDD——每条先写失败测试，跑红，改实现，跑绿，最后全量回归。

## 背景

<原计划> 已交付（<commit数> 提交、<测试数> 测试全绿），但验收发现以下可改进点。本计划只做收尾打磨，不动架构。

---

## Fix N（P1 Bug）：<一句话标题>

**问题**：`<file>:<line>` <现象描述>。<为什么是 bug / 与哪个原则冲突>。

**修复**：<改什么，一句话>。

**Step 1 失败测试**（追加到 `tests/<file>`）：

\`\`\`js
test("<用例名>", () => {
  // 断言
});
\`\`\`

**Step 2 跑红**：`node --test tests/<file>` → FAIL（<失败原因>）。

**Step 3 实现**：<贴可粘贴的改动，标明 old→new>。

**Step 4 跑绿**。

---

## 全量回归（最后执行）

\`\`\`bash
node --test tests/*.test.mjs tests/<子目录>/*.test.mjs
\`\`\`

Expected: 全绿（既有 <N> + 本次新增全部通过）。

完成后单次提交：`git add <显式文件> && git commit -m "fix(<scope>): <一句话>"`

## Self-Review

- 每个 Fix 防什么 / 补什么 ✓
- 所有修复有失败测试先行 ✓
- 不破坏既有测试（已逐条核对既有断言）✓
- 不动无关既有逻辑（在读取侧去重而非改写入侧，风险更低）✓
```

## Fix 排序原则

按 P1→P2→P3 排。同优先级内，按"修复简单度"排（先简单的，建立绿基线）。

## 与 writing-plans 的差异

polish 计划比新功能 plan 轻：不必有 Goal/Architecture/Tech Stack 四件套头（继承自原计划），但每个 Fix 必须有完整的 Step 1-4 TDD 四步 + 提交。

## 写 polish 计划的纪律

- 每个 Fix 的测试代码必须**可粘贴、能跑红**——不能是伪代码。
- 实现代码标明 old→new，让执行子代理能定位（行号会漂移，以代码内容匹配为准）。
- 若某个 Fix 你自己不确定实现思路，**不要硬写**——标注"此处实现思路待执行者判断"，让子代理在执行时做等价修正并披露。
- 宁缺毋滥：不确定是不是真 bug 的，不要塞进 polish 计划；留在报告"疑似需确认"里。
