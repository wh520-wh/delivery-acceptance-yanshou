# 派修复子代理指南

> 这是 SKILL.md Step 6 的展开。核心：context-free 子代理 + 诚实披露 + 降级路径。

## 何时派

三维度验收完成、polish 计划落盘后，**先停下问用户**：

> "验收完成，发现 N 个改进点，已写成 polish 计划（<路径>）。是否现在派子代理执行修复？还是只要报告 + 计划、修复交给你？"

用户同意才派。这一步是对抗性验收与自动重写的边界——必须有人 ack。

## 派谁

general-purpose 子代理（能跑测试、写代码、做判断）。**不要**用 Explore（只读，不能改）。

## prompt 模板（核心：切断会话上下文）

```
你是资深工程师，按 TDD 执行一份收尾改进计划。计划文件在 <polish 计划绝对路径>。

请先 Read 该计划文件，然后严格按照其中 Fix 1 到 Fix N 的步骤执行，每条都是 TDD：
先写失败测试 → 跑红（确认失败）→ 改实现 → 跑绿（确认通过）。

执行要求：
1. 每个 Fix 严格按计划给的测试代码和实现代码。若计划代码与实际文件现状有出入
   （行号漂移、既有代码不同），以实际文件为准做等价修改，不要盲粘。
2. 每个 Fix 跑一次对应测试文件确认绿，再进下一个。
3. 全部完成后跑全量回归：<回归命令>，确认全绿。如果有既有测试因你的改动而红，
   停下来分析——优先怀疑是自己的改动破坏了契约，不要为了过测试而弱化新测试。
4. 最后按计划末尾的 commit 命令做单次提交。注意：用显式 git add <具体文件>，
   不要用 git add -A（避免把工作树的垃圾/无关未跟踪文件塞进提交）。

执行中如果发现计划某个 Fix 的实现思路有更优解或计划有误，不要擅自改方向——
先在最终报告里说明，并按计划执行（或保守地跳过该 Fix 并报告原因）。

完成后输出报告：每个 Fix 的状态（done/跳过+原因）、各阶段测试结果、
全量回归结果、最终 git commit hash、以及你执行中发现的任何计划未预见的问题
（尤其是计划 bug——计划给的实现代码与既有测试不兼容这类）。
```

## 诚实披露核查（复审必做）

子代理报告里若出现以下措辞，复审时必须核实其合理性：

- "做了等价修正" → 核查：修正是否真的等价？是否弱化了新测试？是否触碰了计划说不该动的文件？
- "跳过某 Fix" → 核查：跳过理由是否成立？是计划 bug 还是执行者偷懒？
- "未用 git add -A" → 核查：commit stat 是否干净，垃圾文件有没有混进去？
- "中途某测试红，重跑即绿" → 核查：是 flaky 测试还是真回归？重跑几次稳定？

## 降级路径

子代理失败时的处理顺序：

1. **重试**：换 agentType（如 general-purpose → claude）或显式指定 model，重试一次。
2. **本人接管**：仍失败 → 主 agent 直接执行 polish 计划（自己跑 TDD），在报告里声明"本环节由主 agent 接管而非独立子代理"。这会牺牲 context-free 的对抗性，但好过卡住。
3. **跳过修复**：也可仅交付报告 + 计划，但必须在报告里**醒目标注**"修复环节未执行，交付未闭环，不可合并"。

判断子代理"失败"的信号：
- 工具报错"模型不可用/无权限" → 降级。
- 子代理产出长时间不动（疑似卡权限弹窗）→ 叫停，捞回已有线索，本人接管。
- 子代理跑崩了测试且无法自圆其说 → 不要让它继续乱改，叫停，本人接管或回炉计划。

## 安全边界

- 子代理只能改 polish 计划里列出的文件 + 对应测试文件，不能动其他。
- 禁止 `git reset --hard`、`git push --force`、合并到默认分支、打 tag——这些要主 agent 拿到用户祈使句授权后才做。
- 单次提交，message 按计划给的；不要拆成多个提交制造"显得干了活"的假象。
